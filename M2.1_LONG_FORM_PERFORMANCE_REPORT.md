## 2. Original performance problems

1. **Unbounded waveform peaks cache** (`vendor/braincut/src/lib/media/waveform.ts`): module-level `Map<string, Float32Array>` with no bound, no LRU, no byte budget. Every computed peak set stayed in memory for the session; only explicit invalidation removed one. With many long clips this grows without limit.
2. **Timeline virtualization had no regression tests**: overscan semantics, boundary conditions, very long sequences and stable visible-item math were only code-inspected.
3. Frame/decode caches were already bounded and audited clean (see §6) — no defect found there during this milestone.

## 3. Waveform cache implementation

- New `PeaksCache` class in `vendor/braincut/src/lib/media/waveform.ts` with:
  - least-recently-used eviction via insertion-ordered `Map` (hit refreshes recency by delete+reinsert);
  - `maxEntries` (default `DEFAULT_MAX_PEAKS_ENTRIES = 64`);
  - `maxBytes` byte budget (default 64 MB) with evict-until-fits and skip-if-oversized behaviour;
  - explicit `delete` / `clear`.
- Module-level `getPeaks` / `computePeaks` / `forgetPeaks` now run on the bounded cache; eviction is memory-only, persisted IndexedDB sets are untouched, and a clip that gets evicted regenerates on its next miss.
- No API break for callers: `getPeaks(mediaId)`, `computePeaks(media, blob, opts)`, `forgetPeaks(mediaId, perSecond?)` keep their signatures.

## 4. Cache budget and eviction behaviour

- Default bounds: **64 entries** / **64 MB** of peak data.
- Cost model: one peak set ≈ `2 × buckets × 4 bytes` ≈ `8 × duration × perSecond` bytes; a 3 h clip at 50 peaks/s ≈ 0.86 MB, so 64 long-clip sets stay inside the byte budget.
- Behaviour verified by tests: LRU order, recency refresh, configurable caps, byte-budget eviction, oversized-entry skip, explicit/repeated invalidation, eviction does not corrupt retained entries.

## 5. Timeline virtualization audit

- `TrackLane.svelte` derives an overscan window `(viewEnd - viewStart) * 0.25` on both sides and culls through `clipsInRange` (end-exclusive `[from, to)` overlap semantics).
- Transitions are culled with the same window.
- Lanes render per track; clip DOM is culled per lane, so rendered clip count is proportional to visible window + overscan, not to timeline length (bounded by track count for lanes).
- No tuning was required by the audit; new regression tests cover empty/single/long sequences, boundaries, negative and fractional windows, overscan, stability.

## 6. Decode/frame cache findings

- `engine/media-reader.ts`: frame pool `FRAME_CACHE = 4`, scrub window `SCRUB_WINDOW = 1`, `MAX_SCRUBS`, `READ_AHEAD = 4`, `MAX_PULLS = 600` — bounded.
- `engine/media-cache.ts`: max readers (8), 512 MB image bound, cursor idle sweep, failure cooldown, release/dispose paths — bounded.
- `media/thumbnails.ts`: `MAX_BITMAPS = 400`, `MAX_SINKS = 4`, `MAX_CONCURRENT = 2`, `MAX_QUEUED = 6` — bounded.
- **Finding: no unbounded retention found in the decode/thumbnails/scrub paths.** No targeted change was needed; the memory-hardening scope of M2.1 is satisfied by the peaks cache + audit.
