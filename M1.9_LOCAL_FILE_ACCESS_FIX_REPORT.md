# M1.9 — Local File Access & Import Failure Investigation

Date: 2026-11-19 · Branch: `feature/pro-editor-rebuild` @ `57ad6b9` · Status: reported, diagnosed, fix completed in the M1.8/M2.0 rounds; **no new source changes in this investigation round** — the defect is environmental, not application code. Nothing committed, pushed, or deployed. Photo-editor `src/` untouched.
Environment under test: OpenCode-embedded Chromium **152.0.7977.167 / Electron 44.9.1** (Win x64), served at `http://127.0.0.1:4175/video-studio/`. The user's regular desktop Chrome is a separate, untested environment.

## 1. The reported message is NOT produced by the application

The user reported: *"The localhost link can't open this file."* Search of the entire `vendor/braincut` source:

- `grep -i "can't open | cannot open | link can | localhost link"` → **0 matches**
- `grep -i "localhost|127.0.0.1"` → 6 matches, all agent-related (`agent/bridge.ts` WebSocket URL, `agent/tools.ts` export-upload destination validation) — none touch media.
- `grep -i "file://"` → **0 matches**
- `grep -i "localhost|file://|blob:"` in media components → no app-constructed media URLs at all.

The actual dialog in the user's screenshot is the embedded browser's native file chooser:

> **"Can't open this file — http://127.0.0.1:4175 can't open files in this folder because it contains system files."** *(buttons: "Choose a different file" / "Cancel")*

That is a Chromium/Electron dialog talking about **itself** (the page's own origin refuses its own chooser). It appears **before** the page can receive any `File`, and the page is never handed the selection — the handle grant and the `File` object do not exist from the app's perspective. This refuses, in this environment, any folder Chromium deems system/managed — `%LOCALAPPDATA%\Temp\opencode\` (the temp folder the test videos lived in) was refused outright.

### Consequence chain
1. User clicks Add media (in this pane even the click itself does not reach the app's handlers — verified: zero captured button clicks from real user input on Save/Add media).
2. My trusted harness click did open the chooser; the user navigated to `Temp\opencode`; the chooser rejected the folder ("system files").
3. The picker promise rejected with `AbortError` → (M1.8-era code) silent no-op; (current code) neutral toast: **"Import cancelled — no files were added"**.
4. The user sees the chooser's own message — "…localhost…can't open…" and reads it as Minu Studio's error. The app never saw a file.

## 3. What was fixed in this investigation window

This report does **not** introduce new editor code. The M1.9 failure was eliminated by the two fixes already applied and re-verified this session (M1.8 completion + M2.0 increment, build `1795093951864`):

1. **Drop path resilience (`collectDrop` / `collect`)** — both Chromium failure modes for `DataTransferItem.getAsFileSystemHandle()` now fall back to `item.getAsFile()`: rejection (`NotAllowedError`) and null resolution. Media-type filtering preserved; rejection reasons preserved for the toast.
2. **Silent-cancel toast (`pickFiles`)** — `AbortError` now shows "Import cancelled — no files were added" instead of silence (previously: invisible no-op that looked like "import did nothing for no reason").
3. **HTML `<input type=file>` fallback** — when the picker is missing or refuses for non-cancel reasons (M1.8).

The drag-and-drop fix is the one that makes the *completion criterion* reachable in the embedded environment, because it is the only gesture path that reliably reaches the page here.

## 5. Root cause (exact)

**The error text originates from the OpenCode-embedded Chromium chooser, not from Minu Studio or any app code.** The app has no media-URL construction anywhere; the failure precedes File delivery (`pickFiles` → `showOpenFilePicker` → Chromium chooser policy layer → refuses protected folders → `AbortError`). In this environment real user mouse clicks additionally never dispatch to Svelte handlers (empirically established for the Save and Add-media buttons), so the click→picker→AbortError→(pre-M1.8 silence) chain is exactly what the user experienced as "the localhost link can't open this file". Contributing app-side defects — silent cancellation and drop import never recovering usable files from `DataTransferItem`s — are fixed in the same window (M1.8: toasts/fallbacks; M1.9 window: null-handle `getAsFile()` fallback).

## 6. Does the completion criterion hold?

> "A user-selected local video can be imported, opened, previewed, and played without the app attempting to open an invalid localhost link."

- **In the embedded pane:** import and preview work via drag-and-drop only (the only user gesture reaching the page). Verified: import → probe → bin → reload → restore. Native-dialog import and click-driven flows cannot complete here (chooser policy + click-dispatch anomaly); **the app never constructs invalid URLs either way.**
- **In regular Chrome (expected, unverified):** no app defect exists on this path; the pre-existing `showOpenFilePicker`/handle + permission/relink architecture (M1-era, exercised in earlier milestones) requires no M1.9 change.

2. Large-file/multi-hour/4K import and playback untested everywhere this milestone.
3. MOV, JPEG, PNG, unsupported-format runtime behavior untested.

## 10. Verdict

**The "localhost link can't open this file" report traces to the embedded browser's chooser refusing the user's folder, not to any Minu Studio code — no app-constructed URL exists anywhere in the media pipeline.** The two genuine app-side defects that made the experience silent and broken are fixed and verified (drag-and-drop now imports real files end-to-end; refusals now surface a message). Full desktop acceptance requires one user run in regular Chrome with a normal (non-protected) picker folder — see M2.0 report §11. Nothing has been committed, pushed, merged, or deployed.
