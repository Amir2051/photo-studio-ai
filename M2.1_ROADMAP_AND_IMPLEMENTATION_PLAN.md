## 2. Product and codebase review

### 2.1 What the product is
`vendor/braincut` (brainCUT) is a browser-local NLE: mediabunny demux, WebCodecs decode/encode, PixiJS/WebGL compositing, gl-transitions, Web Audio, immer undo, `.braincut` JSON projects, IndexedDB + OPFS storage, File System Access handles, proxies (WebCodecs) and conversion (ffmpeg.wasm). It is deployed inside the Minu Studio shell at `/video-studio/` and built to static files in `public/video-studio/`. The vendor README is unusually honest about limits, and `docs/CONTRIBUTING.md` names the two most wanted contributions: **(1) files that don't import or play, (2) performance on big files — "four hours of 4K should scrub as well as four minutes of 1080p."**

### 2.2 Implemented and verified (do not duplicate)
- Import: picker + folder + drag-and-drop, handle-based sources, ≤64 MB copies, relink (single + folder walk), missing-media detection, one-click grant-all, AbortError/refusal toasts, HTML-input fallback, import cancellation with progress UI (M1.8–M2.0).
- Edit: multi-track timeline with viewport virtualization (`TrackLane.svelte` culls clips/transitions to `viewStart/viewEnd` ±25 %), 67 transitions, 54 effects, keyframes, titles, markers, linked A/V, 200-step undo, source/program monitors, preview quality 1/8–Full.
- Media pipeline: mediabunny random-access decode, bounded scrub/pull caches (`media-reader.ts` MAX_SCRUBS/MAX_PULLS), thumbnail pool bounds, waveform peaks in a worker + IndexedDB, proxy generation (mediabunny→H.264/AAC, OPFS, quota preflight, progress, create/remove in context menu), ffmpeg.wasm conversion path (2 GB cap), export (MP4/WebM/MOV/MKV/GIF/WAV, presets, in-memory <400 MB else OPFS scratch, picker→download fallback, cancel, progress).
- Persistence: `.braincut` v1 JSON (references only), autosave + recents, reopen restoration, M2.0 export verified end-to-end (ffprobe H.264/AAC, 8.000000 s).

### 2.3 Implemented but NOT fully verified
- Direct-write save/export picker path in regular Chrome (fallback verified instead).
- Timeline virtualization under genuinely long sequences (code-verified only).
- Waveform/peak and proxy behaviour on multi-hour media (small files only so far).
- Import of JPEG/PNG/MOV/unsupported formats at runtime (code paths exist; harness untested).
- Relink/grant-all at runtime (code-verified; needs real Chrome + moved files).

### 2.4 Known defects / rough edges (from reports + code)
- **Waveform peaks cache is unbounded in memory** — `media/waveform.ts:12` `const cache = new Map<string, Float32Array>()`, filled at `:104`, deleted only on explicit invalidation (`:116`); no LRU/size bound. A 1 h clip at 50 peaks/s ≈ 1.4 MB; hundreds of clips accumulate without eviction. Matches the README limitation "very long sequences are limited by memory… caches, waveforms and thumbnails still add up."
- **Zero unit tests in the exact subsystems that caused M1.8/M1.9 pain**: `media/import.ts`, `media/sources.ts`, `media/proxy.ts`, `media/opfs.ts`, `editor/project-actions.ts`, `export/render.ts`, `engine/media-reader.ts` have no test files (29 test files cover project/engine/export-presets/media-probe/stores/captions/agent only).
- No memory/performance profiling protocol exists; the M2.0 large-file report is honest that nothing large was measured.
- Proxy workflow is manual: `useProxies` defaults **false**, no automatic regeneration sweep when a proxy is missing/invalidated, no "regenerate all" action (per-item only).
- Export size estimate is a content-blind heuristic (`presets.ts:218` bits-per-pixel table) — measured ~5× off on near-static content; labelled "about".
- 39 stale bundle chunks sit uncommitted (intentionally; not a defect, a hygiene note).

### 2.5 Architectural limitations that will block future functionality
1. **Long-form memory growth** (peaks cache, plus accumulated thumbnails/proxies) — blocks the "multi-hour" promise and any future feature that adds per-clip state.
2. **No test seam for media/import/persistence edge cases** — every future milestone touching files/projects will regress silently (as M1.5–M1.9 did).
3. Browser codec ceiling (by design) and ffmpeg.wasm 2 GB conversion cap (by design) — documented, not fixable in-app.

### 2.6 Must-not-regress (existing user-facing behaviour)
Local-first import (picker/folder/drag) with originals never modified; `.braincut` save/reopen with relink; export producing genuine MP4/WebM with progress/cancel; captions; agent/MCP bridge (session-only consent, per-action approval); keyboard shortcuts; offline operation.

## 5. M2.1 scope

**User-facing outcome:** a multi-hour, multi-clip, 4K project scrubs, seeks, previews and exports as smoothly as a minutes-long 1080p one, with bounded, measurable memory — and the user can see the editor's storage/memory state.

**Current problem being solved:** per-clip derived data (waveform peaks) accumulates without eviction; long-sequence behaviour is unaudited and unprofiled; no acceptance protocol exists to prove the long-form promise.

### 5.1 Exact proposed scope (essentials)
1. **Bounded waveform-peak cache** — add an LRU/size-bounded cache in `media/waveform.ts` (keep IndexedDB persistence; evict memory, not data), with unit tests for eviction order/size accounting (pure logic extracted for testability).
2. **Long-form audit of the timeline path** — verify/tune `TrackLane.svelte` virtualization and its 25 % margin for long sequences; confirm clip/marker/transition DOM counts stay flat as clip count grows; confirm the ruler/playhead and waveform drawing stay O(visible). Add pure helpers where logic is testable (range culling already exists as `clipsInRange`).
3. **Decode/frame cache audit** — re-verify `media-reader.ts` (MAX_SCRUBS/MAX_PULLS) and `engine/media-cache.ts` (512 MB image bound) under a synthetic scrub storm; tighten if any path grows monotonically.
4. **Memory profiling protocol** — a small, opt-in diagnostics module (uses `performance.measureUserAgentSpecificMemory()` where available, else `performance.memory`, else manual heap deltas) plus a repeatable test script the user runs in regular Chrome on a representative long file; results recorded in a report (honest numbers, no fabrication).
5. **Regression tests** for the new bounds/eviction logic and any extracted helpers (node-safe, no fixtures).
6. **Documentation** of measured limits (update README "Known limitations" and the M2.1 report with real numbers).

### 5.2 Explicit exclusions
- No new editing features (no multicam angle editing, no motion tracking, no new effects/transitions).
- No change to Save/Export behaviour, project format, persistence layout, or the export-size heuristic.
- No proxy-default flip and no proxy regeneration sweep (separate candidate #3).
- No UI redesign; at most a small storage/memory status readout inside the existing Preferences/cache panel.
- No deletion of the 39 stale bundle chunks; no bundle rebuild beyond what the source changes require.
- No dependency additions.

### 5.3 Technical architecture
- Peaks: `Map` → bounded LRU (e.g., byte-weighted, cap derived from a target such as 256 MB) with `dropPeaks` retained; persistence in IndexedDB unchanged (eviction is memory-only, peaks re-generate from the worker on demand — the worker path already exists).
- Timeline: keep the `viewStart/viewEnd` seam; extract the range math into a tested pure module; margin becomes a constant with a comment; no rendering-model change.
- Diagnostics: new `lib/media/performance.ts` (capability-detecting, mirrors the existing `lib/storage/capabilities.ts` style), no UI beyond an optional readout.
- Tests: vitest, node environment, pure functions only (same pattern as `storage/capabilities.test.ts`).

### 5.4 Data persistence and recovery implications
None. No schema, format, or storage-key changes; eviction only affects in-memory caches; IndexedDB peaks/proxies/projects untouched. Autosave/reopen behaviour unchanged.

### 5.5 UI/UX changes
Minimal and optional: a storage/memory readout (quota + peaks cache size) in the existing Preferences/cache area; everything else invisible. No new dialogs, no changed shortcuts, no changed labels.

### 5.6 Performance considerations
Goal: flat heap under a 10-minute scrub of a long sequence; frame-accurate seek (existing frame-grid math unchanged); no main-thread work added (peaks already worker-side; eviction is O(1) bookkeeping).

### 5.7 Security and privacy
No network, no new permissions, no telemetry leaving the device; diagnostics are local-only and opt-in; consistent with the app's local-first posture.

### 5.8 Required regression tests
- New: peaks LRU eviction (order, size cap, re-generate path), range-culling helpers, cache accounting.
- Existing gates re-run: vendor `npx vitest run` (**303** expected), app `npx vitest run tests` (**99**), root aggregate (**346 + 5 informational**), `npm run check` (**0 errors**).

### 5.9 Acceptance criteria
1. Unit tests for eviction/bounds pass; full suites stay green.
2. A repeatable long-form protocol (script + checklist) is documented and run: ≥2 h timeline, ≥50 clips, 4K sequence if footage permits; scrub + seek + preview for ≥10 min.
3. Measured heap stays bounded (no monotonic growth; report the curve honestly, including the browser used).
4. Frame-accurate seek verified at start/middle/end of the long sequence.
5. Export of a long section still produces a valid file (ffprobe-verified) — no regression.
6. README/report updated with measured numbers; unmeasured items explicitly NOT VERIFIED.

### 5.10 Estimated complexity
- Peaks LRU + tests: small (1–2 sessions).
- Timeline audit/tuning + helpers + tests: small–medium (2–3 sessions; mostly measurement).
- Cache audit under scrub storms: medium (measurement-heavy).
- Diagnostics module + protocol doc: small.
- Overall: **medium** (≈1 week of focused work), dominated by verification rather than code.

### 5.11 Dependencies and blockers
- No new dependencies.
- Verification depends on the user's real Chrome + a long representative file (embedded pane cannot host this); the protocol must be runnable by the user with my script.
- No blocker for starting; the measurement steps are the long pole.

## 7. Risks

- **Measurement risk:** long-form claims can only be proven on the user's machine; the embedded pane cannot substitute. Mitigation: scripted protocol, honest NOT VERIFIED labels.
- **Regression risk (medium):** touching cache eviction could drop peaks that are still on screen. Mitigation: LRU keyed to visible clips first, tests, and keeping the persistent IndexedDB copy so eviction is cheap.
- **Scope risk:** the audit may surface that virtualization needs real rework for very long sequences. Mitigation: time-box the audit first; escalate before changing the rendering model.
- **No data risk:** persistence untouched.
